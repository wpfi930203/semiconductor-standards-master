### 1.2 ★ 新发现：机翻件的第三个缺陷 —— 条款号错位

在做 digest 时发现：**约 20% 的条款号是错的**，规律是 **首位数字被移到末尾**。

验证过程（三重交叉，全部可复核）：

| 语料里写的 | 实际应为 | 验证依据 |
|---|---|---|
| `.32` | `2.3` | **A104F 上下文**：该行夹在 `2.2工作区域` 与 `2.4最高样品温度` 之间 → 只能是 2.3 |
| `.162` | `2.16` | 同上：A104F 第 2 章末条（2.15 之后） |
| `.92` | `2.9` | 同上（2.8 之后） |
| `.21` | `1.2` | **J-STD-020 目录**：`1.1范围` → `.21背景` → `.31术语和定义` → 顺序锁定 |
| `.32.联合行业标准` | `2.3 联合行业标准` | **J-STD-020 正文**：`2.1` → `2.2` → 此条 |

**为什么这条比术语错误更危险**：`.32` 看起来完全像一个正常编号。
如果不做上下文核对，读到的就是 `3.2`（而非 `2.3`）——**错得毫无痕迹**。

**处理**：digest 按确定规则还原并标 `（还原）`；原语料**不改**（保持忠实）。
SKILL.md §0.5 加了显式警示：**引用条款号前必须回英文原文核对**。

| 「线束」 | 键合线 | `wire bond` | 机翻标题 ↔ 英文标题 |
| 「热膜」 | 热超声 | `thermosonic` | 机翻 L69 ↔ 英文 L153 |
| 「针线」 | 针脚焊点 | `stitch bond` | 机翻 L73 ↔ 英文 L162 |

| 错误译法 | 出现在 | 共出现 |
|---|---:|---:|
| 「模具」（die） | 18 个文件 | **237 次** |
| 「粘结」（bond） | 8 个文件 | 89 次 |

| 「偏见」（bias） | 3 个文件 | 6 次 |
| 「线束」（wire bond） | 2 个文件 | 3 次 |
| 「针线」「热膜」「冶金键」「骰子」 | 各 1 个 | 各 1~2 次 |

→ 「die → 模具」一个错误就污染了 **18 个文件 237 处**。
这正是「机翻件不能引用措辞」这条规则的量化依据。

### 1.4 为什么这是「蒸馏」而不是「提取」

单纯的文本提取只给出原文（不可用）。digest 做了三件转换工作：

1. **结构重建** —— 把 PDF 的散乱文本层还原成「条款号 → 标题」的层级表
2. **缺陷修复** —— 条款号按确定规则还原；术语错误标注正确译法
3. **可用性分级** —— 明确写出「能用什么、不能用什么」

净效果：**37 份机翻标准从「完全不可用」变成「可用但需转译」**。

## 2. 引用层级扩展

新增 **L4-OCR** 层（扫描件 OCR 后）：

| 层 | 可引措辞 | 可引数值 | 规则 |
|---|:---:|:---:|---|
| L4 | ❌ | ❌ | 只能声明「已持有」 |
| **L4-OCR** | ⚠ | ⚠ | **可用于理解与索引；引用前必须人工核对原扫描页** |

为什么 L4-OCR 不直接升到 L3：OCR 是个别字符可能出错的过程（实测已见
`Downloadedfromhttp://` 这类空格丢失、`http:llassist` 这类 `//`→`ll` 误识），
与机翻的「系统性译名错误」性质不同，但同样需要核对。

## 3. 军标 OCR —— 从「判定不可行」到「找到可行路径」

### 3.1 第一轮：RapidOCR 判定不可行

**新建 `tools/ocr_military.py`**（生产级）：逐页落盘 / 断点续跑 / 版面还原 / 限页 / DPI 可调。

**性能实测（穷尽式排查）**：

| 尝试 | 结果 |
|---|---|
| RapidOCR + onnxruntime **1.30.0**，dpi 200 / 150 / 100 | **178 / 168 / 130 s/页** |
| 强制 `CPUExecutionProvider`（防 Azure EP 抢路） | **313 s/页（更慢，假设被否定）** |
| 换 onnxruntime **1.22.0**（更常规的 CPU 构建） | det 单段 **36 s**（最快观测值） |
| 实际连续跑（dpi 200） | **236~262 s/页** |

旁证：`pip install` 一个 15 MB wheel 耗时 **20 分钟**；
det 模型对 736×1041 输入耗 36 s（正常机器 <0.5 s）。
→ **根因是执行环境算力/IO 受限**，不是配置问题。
→ 全量 2,229 页需 **22~75 小时**，判定不可行，改走定向 OCR。

### 3.2 ★ 第二轮：发现 Windows 内置 OCR，快 5~10 倍

关键判断：这是 **Windows** 机器，系统自带 `Windows.Media.Ocr` 引擎，
通常比基于 onnxruntime 的方案快一个量级。

**过程**（三次尝试）：

| 尝试 | 结果 |
|---|---|
| 从 Bash 调 `powershell.exe` | ❌ 被安全策略拦截 |
| `pip install winsdk`（WinRT 全量绑定） | ❌ 无 Python 3.13 wheel，构建失败（耗时 20 分钟） |
| **`pip install winrt-*` 拆分包** | ✅ **成功** |

```python
from winrt.windows.media.ocr import OcrEngine     # 可用语言: zh-Hans-CN
```

**实测速度对比（同机同日同页）**：

| 引擎 | 速度 |
|---|---|
| RapidOCR + onnxruntime CPU | 36 ~ 262 秒/页 |
| **Windows.Media.Ocr (WinRT)** | **1.6 ~ 30 秒/页** |

分语种看：**GJB 中文约 3~5 s/页**、**883 英文约 12~25 s/页**。

于是把 `ocr_military.py` 改为**双引擎**（Windows OCR 首选 / RapidOCR 回退）。

### 3.5 OCR 的三个已知误差类型（都实测到了）

| 类型 | 实例 | 能否自动修 |
|---|---|---|
| 字符误识 | `http://` → `http:ll`；`Stabilization` → `Stab 山 zation` | 部分（做了确定性修正表） |
| 词间空格丢失/插入 | `DownIoadedfromhttp`；中文被切成「微 电 子 器 件」 | **是**（已写 CJK 空格折叠） |
| **★ 标题错位** | 目录页个别标题被 OCR 提前输出，使标题与方法号错位（`Stabilization bake` 排到 `1008` 之前） | **否** —— 这是读序问题，无法靠解析修复 |

→ 因此定下规则：**方法号可信（用于定位）；标题为 OCR 产物，引用前必须核对原页**。
`mil-methods.json` 里带 `validation` 字段逐份给可信度自检（覆盖率 + 单调性）。

### 3.6 一个自纠：解析器 first-cut 是错的

初版解析器把标题行判定写得过严（字符类没包含全角标点 `，、．`），
导致合法标题被判为「非标题」而跳行，**结果 883K 的 1001 被配成 1002 的标题**。

发现方式：人工抽看输出时注意到 `1010 → Thermal shock`（而 1010 应是 Temperature cycling）。
修正：把「方法号行的紧邻下一非空行」直接作为标题，并放宽标题判定。
修正后标题覆盖率从 ~60% 升到 92~95%，单调性也通过。

> 这一条留档的意义：**指标好看（90 个方法号）不等于数据对**。
> 如果只看「解析出 90 个方法号」就收货，配错的标题会被当成事实写进 skill。
> 是「抽查 + 与已知常识比对」这个动作抓出来的。

## 7. 一句话总结

> **「蒸馏机翻标准」这件事的价值不在多存了 37 份文本，而在发现机翻件有三个独立的缺陷**
> （术语被译坏 / 条款号错位 / 表格丢符号），并对每一个都给出可执行的补救
> （纠错表 / 还原规则 / 交叉核对）。

> ——36~236 秒/页是量出来的，不是猜的；下一步该换什么环境也就清楚了。
